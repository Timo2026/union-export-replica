## 一、结论速览

当前交付物处于**「能看不能跑」**状态：README 与 PPT 描绘了一个完整的"AI 工艺大脑"，但实际打包的代码存在一个**致命缺陷** —— 核心业务代码目录 `src/` 整个缺失，主服务 `app/main.py` 启动即崩溃。这直接解释了 Hackathon 仅得 31.3 分、以及商业评估中"AI 可嵌入性"仅 1 分的原因。

**核心矛盾一句话**：宣称「离线优先、多模型自适应、5 专家会议、TOT 三管道竞争、可解释审计链」，但交付包里这些能力的源代码全都不在，只剩一个壳（前端 + 精简版 + 配置文件）。

## 三、致命问题清单（按严重度分级）

### 🔴 P0 — 阻断性问题（不修无法交付）

**P0-1：`src/` 核心代码目录整个缺失**

`app/main.py`（3998 行）第 34–57 行导入 23 个 `src.*` 模块：

```
src.ai_engine.engine / ollama_engine / openai_engine
src.core.environment_detector / model_auto_loader / model_registry / skill_auto_loader
src.data.rag_engine
src.neuro_core.conflict_check / reasoning_chain / schema_validator / serial_expert
src.runtime.cad_pipeline_tot / event_bus / export_bundler / history_lookup / progress_reporter
src.runtime.quote_adapter / skill_caller / step_generator / step_generator_dual / step_parser
src.safety.audit_logger
```

- 交付目录（文件夹 + zip 包，共 143 个条目）中**不存在 `src/`**。
- 结果：`python -m uvicorn app.main:app` 在 import 阶段即抛 `ModuleNotFoundError: No module named 'src'`。
- **完整版永远无法启动**，只有 `main_lite.py`（精简版）能跑。

**P0-2：AMD/ROCm 无任何落地**

比赛主题是 Radeon/ROCm，但 PR Notes 自述 *"no native ROCm-specific code, but architecture is backend-agnostic"*。对 Track 2 评审而言，这等于**交了一张白卷**——"架构上可以切换 ROCm"不等于"用了 ROCm"。这是失分的最直接原因，也是商业评估"AI 可嵌入性 1 分"的根源。

**P0-3：硬编码密钥泄露（安全隐患）**

`config/models.json` 第 73 行，`step-3.7-flash` 的 `api_key` 为**明文真实密钥**：

```json
"api_key": "7z5spS…UpZ8T（64 位真实 key 已于本交付副本脱敏；交付前务必轮换，并统一改为 ${STEPFUN_API_KEY}）"
```

（注：紧邻的另一条同模型配置用了 `${STEPFUN_API_KEY}` 占位符，说明作者知道应脱敏，但仍有一条漏了。）交付前必须轮换该密钥并全部改为环境变量。

### 🟠 P1 — 严重问题（影响评审与可信度）

**P1-1：功能声明与代码实现严重不符**

- README 宣称"24 种材料 × 14 种表面处理"，`main_lite.py` 实际 `MAT_COEFS` 仅 8 种材料、`SURF_COEFS` 仅 8 种表面处理。
- 宣称"5 专家串行会议""TOT 三管道""可解释审计链"，但 `config/experts/*.yaml` 只有 Prompt，`config/skills/*.yaml` 只有 schema，**对应执行代码（serial_expert.py、cad_pipeline_tot.py 等）缺失**。
- 评审若抽查代码，会立刻判定"PPT 大于实际"。

**P1-2：版本号四处打架**

| 位置 | 版本号 |
|------|--------|
| README 标题 | v12.0.0-fusion |
| `app/main.py` | 12.0.0-fusion |
| `app/main_lite.py` 头注释 | 11.0.4 Lite |
| `app/main_lite.py` 启动打印 | 11.0.5 |
| `CNC_AI_Brain_启动.bat` 标题 | 11.1.0 |

评审看到会认为项目管理混乱。

**P1-3：交付包卫生极差**

- `data/exports/` 下混入 **100+ 个测试产物 zip**（bundle_*.zip、bundle_test-*.zip），最老至 2026-07-04。
- `app/__pycache__/` 混入 Python 3.10 与 3.11 两套 `.pyc` 缓存。
- `data/audit.db` 1.4MB、`data/orders.db` 24KB 等运行时数据直接打包。
- 说明作者是**直接把开发目录压缩**，未做任何交付前清理。

## 四、逐项修复方案（可执行）

### 修复 P0-1：补齐 `src/` 源码

这是唯一"必须做"的事。两种路径：

**路径 A（首选）：找回源码**。源码应在作者本地 Git 仓库 `github.com/Timo2026/Radeon-hackathon-2026-07/tree/main/Timo_CNC-AI-Brain-v12.0-Fusion` 的 `src/` 分支里，可能因 `.gitignore` 或打包时漏选而缺失。从 Git 历史 `git checkout` 找回并纳入交付包。

**路径 B（兜底）：降级交付为"精简可用版"**。若源码确已丢失，则：
1. 将 `main_lite.py` 升级为唯一主入口，删除 `main.py` 对 `src.*` 的依赖。
2. 把 `main_lite.py` 内的报价引擎（`MAT_COEFS`/`SURF_COEFS`/`calc_quote`）、冲突检测（`CONFLICT_RULES`/`check_conflict`）、STEP 生成、打包导出作为**真实能力**在 README 中如实重写，砍掉所有"5 专家/TOT/审计链"等未实现宣称。
3. 诚实标注：完整版（含 src）见 GitHub 仓库，本交付包为 Lite 版。

### 修复 P0-2：补 ROCm 落地证据

哪怕最小化，也要有**可验证的 ROCm 证据**，例如：
1. 在 README 增加一节「ROCm 实测」，附 `rocm-smi` 输出截图、PyTorch ROCm 版 `torch.cuda.is_available()` 返回 True 的截图。
2. 若本地模型跑在 AMD GPU 上，附 `vllm` 或 `llama.cpp` 的 ROCm 启动日志（HIP 设备识别）。
3. 若无硬件，至少提供 Dockerfile：`FROM rocm/pytorch:rocm7.x`，并写明 `docker run --device=/dev/kfd --device=/dev/dri` 的部署命令。
4. `config/models.json` 中本地模型描述应标注实际推理后端（vLLM ROCm / LMStudio 走 Vulkan/ROCm 等）。

### 修复 P0-3：密钥脱敏

1. **立即轮换** `stepfun` 的 API Key（已泄露，视为作废）。
2. 删除 `models.json` 中所有明文 key，统一用 `${STEPFUN_API_KEY}` 占位符。
3. 在 `.gitignore` 增加 `.env`，README 说明通过环境变量注入。

### 修复 P1-1：README 如实化

把 README 的「核心特性」分成两栏：**已实现（Lite 真实可用）** vs **规划中（需 src）**，避免评审失望。报价引擎的 8 种材料、8 种表面处理要如实写，不要再写 24×14。

### 修复 P1-2 / P1-3：统一版本 + 清理交付包

1. 全局统一版本号为单一来源（建议 `config/version.txt`，所有地方读取它）。
2. 交付前执行清理：删除 `data/exports/*.zip` 测试产物、`__pycache__/`、`.pyc`、`*.db`、`data/step` 与 `data/uploads` 下的测试文件。
3. 保留一个干净的样例 STEP/STL 用于演示即可。

## 六、商业可行性提升（结合商业评估结论）

回到商业评估的三维框架，`#158` 当前 **Dig 2 / Dec 2 / Emb 1 = 5 分**，是"独立工具"而非"嵌入型 AI"。要提升商业价值，需补三个短板：

### 短板 1：数字化基础（Dig 2 → 目标 7+）

CNC 报价 + DFM 检测的真实场景**已有成熟的数字化底座**，但项目完全没对接：
- **ERP/MES**：工厂报价单、BOM、工艺路线都在 ERP/MES 里。
- **PLM/CAD**：STEP 文件本身就是 PLM 的产物，本可天然对接。
- **建议**：在 `cnc_quick.py` 增加「ERP 报价单导入」接口（CSV/XLSX 解析订单），用 `data/orders.db` 建立历史报价库，让 AI 从"重新计算"变成"基于历史订单校准"。

### 短板 2：决策依赖人工（Dec 2 → 目标 7+）

DFM 检测 + 报价本质是**强人工决策节点**，项目已有「Shadow Mode + 免责声明」，但没把它做成卖点：
- **建议**：把 `wrap_shadow()` 的"人工确认制"升级为**留痕审批流**——AI 给出报价/工艺建议后，强制工程师点击确认并留审计记录（`audit.db` 已有雏形），形成"AI 建议 + 人工拍板"的合规闭环。这正是「AI copilot 而非 AI 替代」的正确姿势。

### 短板 3：AI 可嵌入性（Emb 1 → 目标 7+）

当前是独立 Web 服务，无法嵌入工厂现有工作流：
- **建议**：主打 `MTClaw Function Router` 的 `cnc_conflict_check` / `cnc_quote_calc` 两个 function 工具（已在 `cnc_functions.jsonl` 定义），把它们包装成**可被任何 Agent 框架调用的标准 Function Calling 接口**，让工厂的客服机器人、ERP 的询价模块直接调用，而不是另起一个独立系统。

### 商业定位重述

修复后的正确叙事应该是：**「嵌入工厂询价/工艺审批流里的 CNC 报价与 DFM 合规 copilot」**——对接 ERP 历史订单 + 保留工程师审批节点 + 以 Function 工具形式嵌入现有系统，而非"一个独立的 CNC 报价网站"。这与商业评估中"工业设备维护/MRO 赛道"的推荐逻辑一致（痛点明确、付费意愿强、需嵌入现有工作流）。
